═══════════════════════════════════════════════════════════════════
BUDGET APP - HOW TO RUN
═══════════════════════════════════════════════════════════════════

FIRST TIME
──────────
1. Make the OFFLINE COPY of .env BEFORE the first account exists.
   .env is the only key to everyone's data. There is no recovery phrase
   and no other way in (decided 2026-09-14). Keep the whole file in at
   least two places, off this machine and off the company network - for
   example a password-manager entry AND an encrypted USB stick, stored
   apart. Never beside the .budgetbak backups, never in git.
   See "THE OFFLINE .env COPY" below.

2. python -m venv .venv
   .venv\Scripts\activate
   pip install -r requirements.txt

3. .env is already filled in: the DB settings come from QUOT's .env and
   every key is generated. Nothing to do - just do not lose it (step 1).

4. alembic upgrade head                 # DONE 2026-09-11 - schema ZBDGT exists
   Create your account on the sign-up screen: open the app, "Create an
   account", and enter the code from REGISTRATION_CODE in .env. The FIRST
   account becomes admin - make it yours.
   python scripts/bootstrap_user.py     # OPTIONAL fallback: same account,
                                        # from the command line
   python scripts/seed_categories.py    # (Phase 3) default categories


RUN THE BACKEND
───────────────
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000

  App     http://localhost:8000/ZBDGT
  Health  http://localhost:8000/ZBDGT/api/v1/health
  Docs    http://localhost:8000/ZBDGT/api/v1/docs   (only with DEBUG=True)


RUN THE FRONTEND (development, with hot reload)
───────────────────────────────────────────────
cd frontend
npm install          # first time only
npm run dev          # http://localhost:5173/ZBDGT/  - proxies /ZBDGT/api to :8000

Develop against :5173. It has hot reload; :8000 serves the last build.
Keep uvicorn running alongside it, or every API call fails.


BUILD THE FRONTEND (before committing or deploying)
───────────────────────────────────────────────────
cd frontend
npm run build        # type-checks, then writes into ../app/web/static/dist/

Then COMMIT app/web/static/dist/. It is deliberately not gitignored.
The server has no Node and no npm - it only serves these bytes.
Deploy is: copy the release zip over (misc/DEPLOY.md). Nothing is built
on the server, ever.
uvicorn picks up a new build without a restart (it re-reads the manifest).


TEST ON YOUR PHONE
──────────────────
uvicorn app.main:app --host 0.0.0.0 --port 8000
Browse to http://<your-pc-ip>:8000/ZBDGT on the phone, then
Share -> Add to Home Screen for the standalone PWA (Phase 8b).


TESTS
─────
pytest                                      # everything, ~30 s
pytest -m "not slow"                        # the quick ones, ~12 s
pytest tests/test_crypto.py -v              # never skip these
pytest tests/test_crypto_performance.py -s  # prints the benchmark number

The tests use throwaway keys and an in-memory SQLite database. They never
read your real keys and never touch the company database - except the
ones marked `db`, which are skipped unless you ask for them:

set ZBDGT_DB_TESTS=1
pytest tests/test_db_mssql.py tests/test_crypto_performance.py -s

Those create a throwaway inactive user and delete everything they made.


BACKUP  (Phase 8a - so the company DB is not your only copy)
────────────────────────────────────────────────────────────
python scripts/backup.py --user-id 1      # full encrypted .budgetbak (needs no key)
python scripts/backup.py --all            # every active user
python scripts/restore.py FILE --target-user-id 3 --verify   # dry run + diff, writes nothing
python scripts/restore.py FILE --target-user-id 3 --fresh    # into an EMPTY account
python scripts/restore.py FILE --target-user-id 3 --merge    # add to it, skip duplicates
   ... restore.py opens the file with the master key in .env (current or
       retired).python scripts/verify_backup.py --user-id 1                  # round-trip fidelity check

Backups are written to BACKUP_DIR/<user_id>/ - automatically 5 minutes
after a change and at sign-in when the newest is over a day old, or from
More -> Backup & data -> Back up now. That screen also downloads them,
restores (Check / Add to mine / Into empty), and exports or imports CSV.

A restore goes INTO AN EXISTING ACCOUNT. On a new server: put the
offline .env copy in place, sign up, then run scripts/restore.py with
--target-user-id set to the new account. The app's own Restore button
opens only the signed-in account's own backups (same user id), so a
restore onto a new server is always the script.

The .budgetbak file is encrypted end to end, so ON ITS OWN it is safe on
a USB stick or in cloud storage. It carries the DEK wrapped under the
master key: a backup file plus the .env copy opens everything. Never
keep the two in the same place.

Run --verify occasionally. A backup you have never restored is not a
backup, and here the cost of finding out is everything.


IMPORT FROM THE "BUDGET" PHONE APP  (DAT-21)
────────────────────────────────────────────
1. In the Budget app, export a backup (.xlsx). Keep it in budget_app_backup\ -
   the folder and every .xlsx are gitignored, because the file is your real
   finances in plain text.
2. Sign in to THIS app, then More -> Backup & data -> Import from Budget App,
   and choose the file. The preview writes nothing: accounts, categories,
   transactions, and what is left out (the old app's balance adjustments).
3. Type each account's balance TODAY as the Budget app shows it - a card or a
   loan as the amount owed. People you lent to or borrowed from are prefilled.
   The history comes in as it is; each opening balance is set so today matches.
4. Import. Afterwards: set each card's statement closing and due day (Edit on
   the card) - the file does not carry usable ones - and type each card's
   bills from its own app if you pay it by monthly bills.
Importing a later export again adds only what is new (matched by name,
duplicates skipped). The file is read in memory and never stored on the server.

ROTATING THE MASTER KEY
───────────────────────
Dry-run every step first. In this order:
  1. python scripts/rotate_keys.py --new-key --dry-run
     python scripts/rotate_keys.py --new-key
       .env gets a new key; the old one moves into BUDGET_RETIRED_KEYS.
  2. Restart the app (IIS: recycle the ZBDGT pool) so it loads the new key.
  3. python scripts/rotate_keys.py --rewrap --dry-run
     python scripts/rotate_keys.py --rewrap
       Interrupted? Run it again - it carries on.
  4. Replace the offline copy of .env TODAY, then
     python scripts/env_fingerprint.py --compare <the copy>
Never delete a retired key while a backup made before the rotation might be
needed - only that key opens it. Rotation does not lock out someone who
already unwrapped a key; after a leak, every user also rotates their own key.


ADDING ANOTHER USER
───────────────────
Registration is never open. Anyone signing up needs the code in
REGISTRATION_CODE (.env), and MAX_USERS caps the total. Change the code
to cancel every invitation you have handed out. They sign up at
/ZBDGT/register. The first account created becomes the admin.

Each user gets their own encryption key, and nobody can read anyone
else's data from inside the app - including you, as admin. Users keep
no recovery secret. A user who forgets their password uses "Forgot
your password?" on the sign-in screen and gets a link by email (SEC-30).
Their data is untouched, because the password never wrapped their key -
which also means anyone who can read their mailbox could reset it. Tell anyone you add the honest
version too: whoever holds .env AND the database can read every
account. That is the server owner.


PASSWORD RESET EMAIL (SMTP)
───────────────────────────
Set in .env: SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASSWORD (for Gmail an
App Password, not the account password), SMTP_FROM (= SMTP_USER for Gmail),
SMTP_FROM_NAME. Empty SMTP_HOST turns reset-by-email off, and the sign-in
screen tells people to ask you instead.
APP_PUBLIC_URL is where the emailed link points: http://localhost:5173 in
.env for development, https://delca.noahapplication.com in web.config.
If a reset email never arrives: logs\app.jsonl says "Email could not be
sent" with the reason; check the App Password is still valid.

THE OFFLINE .env COPY  (SEC-31 - the only insurance against losing .env)
═══════════════════════════════════════════════════════════════════
WHAT: the WHOLE .env file, not just the master key.
  BUDGET_MASTER_KEY          opens every user's key. Without it, ALL
                             data of ALL users is unreadable
  BUDGET_RETIRED_KEYS        opens backups made before a master-key
                             rotation
  BUDGET_BLIND_INDEX_PEPPER  finds an account by its email. Without it
                             nobody can sign in until every index is
                             rebuilt by a script
  PIN_PEPPER, JWT_SECRET_KEY, SESSION_SECRET
                             losing these only signs everyone out and
                             clears PINs - copy them anyway
  REGISTRATION_CODE, DB_*    convenience

WHERE: at least two places. None of them the app server, none of them
  in git, none of them beside the .budgetbak files. A password manager
  plus an encrypted USB stick kept somewhere else is a good pair.

WHEN TO REFRESH IT: the same day .env changes - after generate_keys.py,
  after rotate_keys.py (the old key moves into BUDGET_RETIRED_KEYS),
  after any edit. A stale copy cannot open anything written under the
  newer key.

CHECK IT, DO NOT TRUST IT: python scripts/env_fingerprint.py --compare <copy>
  prints a non-secret fingerprint of each key. Run it on the server and
  against the copy and compare. After every refresh, and every few
  months besides.


IF YOU LOSE .env
────────────────
  1. Copy the offline copy back into the app folder as .env.
  2. Restart the app. /ZBDGT/api/v1/health should say the master key
     loaded.
  3. Everyone signs in as before. Nothing else to do.

Do NOT run generate_keys.py to "fix" a missing .env: new keys open
nothing that already exists.

IF THE OFFLINE COPY LEAKS
─────────────────────────
Whoever has it plus the database (or any .budgetbak) can read every
account. In this order:
  1. Rotate the master key (ROTATING THE MASTER KEY, above).
  2. Rotate every user's DEK (Settings -> Rotate my encryption key).
     Step 1 comes first so the new keys are not wrapped under the
     leaked one.
  3. Make a fresh offline copy, destroy the old copies, and delete
     backups written before the rotation.

IF YOU LOSE .env AND EVERY COPY
───────────────────────────────
All data, for every user, is gone. Permanently. No reset, no support
ticket, and the DBA cannot help. There is no second key: that is the
trade for not asking every user to keep 12 words on paper.

THE AI ASSISTANT  (misc/AI - watsonx through the company IAM service)
═══════════════════════════════════════════════════════════════════
ON / OFF: AI_ENABLED in .env, then restart. Off means nothing is loaded
and nothing is called. Each person also turns it on for themselves
(More -> Assistant); AI_ALLOWED_USER_IDS limits who may.

WHAT LEAVES THE SERVER: the question, and the figures and the account,
category and goal names needed to answer it - to IBM watsonx (us-south).
Never an email, a note, a receipt or a row. ZBDGT stores no question and
no reply, in the database or in a log: only how many were asked.

THE KEY IS NOT OURS. The watsonx API key lives in the company IAM
service, shared with QUOT, DMS and STWRD. ZBDGT fetches it when a
question is asked, keeps it in memory for 5 minutes, and never writes
it anywhere. So there is nothing to rotate or back up here.

CHECK IT:  python scripts/ai_health.py     (or Admin -> Check the connection)

  Key: "IBM Cloud rejected the API key from IAM"
      The key in IAM's record is expired or deleted. It is IAM's record,
      not ours: tell its owner. Anything else using that record (QUOT,
      DMS, STWRD) fails the same way. Nothing in ZBDGT's .env fixes it.
      When the key is replaced the assistant recovers by itself within
      5 minutes - no restart.
  Key: "...IAM's record still marks this key expired"
      The key works, but the record's expiry fields are stale. Harmless
      here; mention it to IAM's owner.
  Key: "could not be loaded from IAM" / "IAM returned no credentials"
      IAM_MANAGEMENT_URL or COMPANY_NAME is wrong (copy both from STWRD's
      .env), or this machine cannot reach IAM.
  Model: "timed out after 30s"
      IBM is slow or unreachable. Questions are answered from the app's
      own sentences meanwhile ("Answered straight from your figures").
  Model: "model '...' was not accepted"
      WATSONX_CHAT_MODEL names a model the project does not have.

While any of these is wrong the rest of the app is untouched, and every
answer still carries the right figures - they never came from the model.

WATCH IT: Admin shows, per day, questions / answered without AI / tokens
for all accounts together. Above 10% answered without AI in a day: look at
logs\app.jsonl for "Assistant turn ... reason=" (timed, unknown_figure,
advice, ...). The line never holds the question or the reply.

AFTER CHANGING A PROMPT, A SKILL OR THE MODEL: python scripts/ai_eval.py
and read the replies. Every wrong answer so far had true numbers in it.

DEPLOY TO THE SERVER  (IIS, same host as QUOT)
═══════════════════════════════════════════════════════════════════
Updates are COPIED to the server (there is no git remote). The zip holds
only committed files, so it can never carry your local .env or data.

FULL GUIDE: misc/DEPLOY.md - prerequisites, the first deploy, every update,
rolling back, and what to check when something is wrong. The short version:

EVERY UPDATE
  a. On your PC:  cd frontend  then  npm run build   (the server has no npm)
  b. Commit everything, including app/web/static/dist/.
  c. python scripts/make_release.py   -> release\zbdgt-<commit>.zip
     (it refuses while anything is uncommitted - that would be missing)
  d. On the server, in C:\inetpub\wwwroot\ZBDGT:
       - DELETE the folders app\, alembic\ and scripts\ (so files removed
         from the code, like old bundle files, do not linger)
       - unzip the release over the folder
       - NEVER delete or overwrite  .env  uploads\  backups\  logs\
  e. If requirements.txt changed: step 4 below (dry run first).
  f. If alembic\versions gained a file: ask the DB owner, then
       C:\inetpub\wwwroot\FAST-PYTHON\.venv\Scripts\alembic upgrade head
     (local development shares the SAME ZBDGT schema - usually it is
      already applied from your PC)
  g. Recycle the ZBDGT app pool, then open /ZBDGT/api/v1/health.
  h. The AI assistant stays off until AI_ENABLED=True is in the server's
     .env - misc/DEPLOY.md, "Turning on the AI assistant".

FIRST DEPLOY
1. Steps a-c above.
2. On the server, unzip it into  C:\inetpub\wwwroot\ZBDGT
3. Copy .env into that folder BY HAND. It is not in git, and it holds
   the master key and the database password. Check it matches the
   offline copy (env_fingerprint.py) - they must be the same keys.
4. Preview what installing would change in the venv QUOT also uses:
     C:\inetpub\wwwroot\FAST-PYTHON\.venv\Scripts\pip install -r requirements.txt --dry-run
   Install for real once the preview looks safe.
5. In IIS Manager, add an application named ZBDGT pointing at that
   folder. web.config is already there: one worker, /ZBDGT, no secrets.
6. Open  https://delca.noahapplication.com/ZBDGT/api/v1/health
   It should report the database reachable and the master key loaded.
7. On the server, in the app folder, once:
     C:\inetpub\wwwroot\FAST-PYTHON\.venv\Scripts\python scripts\benchmark_fetch.py
   Read-only. Under 1500 ms and the encryption design stands as it is.
   (From your PC it reads ~2.3 s - that is your internet link, not the app.)

The app itself:  https://delca.noahapplication.com/ZBDGT
