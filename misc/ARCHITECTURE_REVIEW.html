1 · Bill placement: one module answers "which bill does this charge land on?"

Strong

Files account_service.py _bills 1333–1463, _bill_on_or_after 1473, _dues_view 1225, 1287–1289, 1432/1571 · projection_service.py _lands_on_bill 416–431, _bill_items 317–367 · installment_conversion.py default_start 99–108, 254–256 · recurring_service._loan_payments 1302+, plans_owed 589–597

Problem

The ACC-35 / REC-14 rule "an installment joins the first bill due on or after its date; any other charge takes its statement's due date" is written three times with no shared code. _lands_on_bill's own docstring says it "has to ask the question exactly the way _bills answers it (fixed 2026-09-16)" — it drifted once already. "Due now = overdue + next" is written 4×, the "payment into a card" predicate 2×, and there are two separate FIFO payment allocators (card bills, loan plans). The last two feature commits (money sent from a card joins its bill, …uses up its spending limit) both had to touch this.

Solution

Pull the placement rule, the due-now rule and FIFO allocation into one pure module next to date_utils.statement_period (the way interest.py / payoff.py already live in core/utils). It takes a card's days plus charges and payments and returns bills. _bills, the projection and installment conversion all ask it; _lands_on_bill and default_start's card branch are deleted.

Benefits

Locality: the next "X joins its bill" rule changes one file, and projection can't disagree with the card page by construction. Leverage: three callers, one answer. Tests: today agreement is only checked end-to-end through projection_service.project; the module's interface becomes the test surface — plain dates and Decimals, no DB, no cipher.

2 · "What you owe" is one field on every account view

Strong

Files account_service.AccountView / CreditView.owed_with_plans · payoff_service._owed 110–114 · skills/cash.py 19–20 · frontend/src/lib/accounts.ts owedWithPlans 384–389, isOwed 377

Problem

The server only sends owed_with_plans for cards. For a loan, three callers rebuild it from balance + plans_unbilled — and they already disagree: payoff clamps with max(-balance, 0), the AI skill and the frontend don't. A borrowed account overpaid by ₱100 with a ₱5,000 plan shows ₱4,900 on its page and in the assistant, ₱5,000 in the payoff planner. The assistant's rule "a skill must report the figure its screen shows" is only true by coincidence here.

Solution

Put owed (incl. plans) on AccountView for every owing account, computed once in _view. Delete payoff._owed, the fallback branch in cash._money_in, and the arithmetic in owedWithPlans (it becomes a field read). Decide once whether it clamps.

Benefits

Deletion test passes: removing the three copies concentrates the rule rather than moving it. Locality: REC-14 changes in one place. Tests: one assertion in test_accounts.py pins it; the frontend loses untested money arithmetic.

3 · Account views that fetch their own postings

Worth exploring

Files account_service.list_accounts / get_account 548–573, _view 1132–1213, 5 lazy imports (808, 1100, 1107, 1120, 1502) · callers projection_service 186/248, skills Context.accounts 72, payoff_service 83, skills/afford

Problem

The interface to get an account's balance includes "pass postings=transaction_service.postings(...) yourself". Forget it and every balance is silently zero. afford builds the list twice. _view is a long chain of replace(view, …) encoding the cash_amount priority (dues/bills → set-aside → balance), and _plan_charges (58 lines, 3 lazy imports) re-classifies transaction kinds inside account_service.

Solution

Make "the user's accounts as of today" a module that takes (db, cipher, today) and reads postings, plans, goals and bills itself from the working set. Callers stop wiring. The replace chain becomes one place that decides cash_amount. Also delete the dead _unpaid_installments / recurring_service.unpaid_by_account (no callers).

Benefits

Leverage: 4+ callers lose a parameter they can get wrong. Locality: the lazy-import web shrinks to one place. Tests: the "forgot postings" failure mode disappears instead of needing a test. Trade-off: ties the view to the working set — fine, it's the only source of postings anyway.

4 · Account type rules in one place (server) and sent to the client

Worth exploring

Files account_service.OWES 137, COUNTS_IN_CASH_ON_HAND_DEFAULT 84–93 (resolved at 642, 1172, 1731) · budget_app_import_service.OWED_TYPES 74 · installment_conversion.SPREADS_ON 53 · skills/cash.py 19 · cash_on_hand 576 vs cash_history 632/_counts_in_cash 640 vs net_worth 653 · client: isOwed, inline copies in TransactionSheet 190/321/489/534, AccountDetail 242/251, Accounts.tsx notCountedIsNews 84

Problem

"Credit or borrowed" is spelled out 4× on the server and 7× on the client; "counts in cash on hand" is decided 3 ways (live accounts, history over raw dicts, net worth) and its default resolved 3×. Adding account type #9 means a grep, and ACC-39's untracked wallet already had to be threaded through each copy by hand.

Solution

One small server module of account-kind predicates (owes, counts in cash by default, can spread into a plan) used by every service, and per-account booleans on the wire (owes, counts_in_cash, spreadable) so the client reads rather than re-decides. cash_history calls the same predicate.

Benefits

Locality: a new type is one edit. Leverage: client logic collapses to field reads. Tests: a table test over the 8 types replaces nothing-at-all today on the client. Lower urgency than #1–2: the copies agree today.

5 · AI companion skills declared once

Worth exploring

Files assistant_service/router.py SKILLS 41, _KEYWORDS 47–83, _skill_by_rules 371–399, ROUTE_PROMPT 453–466, NOT_CARRIED 514, rules-only list 636 · skills/__init__.py 93–116 · turn._SCREENS/_ALERTS 77–87

Problem

A new skill touches 6–9 parallel lists that nothing keeps in step. They have already drifted: ROUTE_PROMPT lists 13 skills, SKILLS has 17. The router is the hottest assistant file (8 commits in two weeks, mostly follow-up/carry rules).

Solution

Each skill module declares itself: name, keywords, one prompt line, model may route here, follow-ups carry it, and its runner. The router and prompt are built from that registry; the dispatch table and lazy imports go away. Precedence rules stay in the router where they are genuinely relational.

Benefits

Locality: a skill is one file. Tests: one test asserts every registered skill appears in the prompt and is reachable — catching today's 13-vs-17 drift. Safety rules (drafts never model-routed) become a declared flag instead of membership in a list far from the skill.

6 · The transaction draft: wallet resolution and validation move behind the server's interface

Speculative

Files frontend/src/components/TransactionSheet.tsx (1190 lines, 32 useState, open effect 277–389, problem 514–531, save 591–659) · transaction_service _positive, _clean_transfer, validate_splits · account_service.untracked_cash

Problem

The most-edited file in the repo holds ten concerns. Saving a lent/borrowed transfer from the wallet is two requests orchestrated by the client (POST /accounts/untracked, rewrite the body, POST the transaction) for a rule CLAUDE.md says the server owns. problem() re-implements six server validations. No tests cover any of it.

Solution

Let POST /transactions accept "the untracked wallet" as a side and resolve it inside transaction_service in the same commit; let the sheet show the server's problem codes instead of duplicating them (keeping only instant hints like "amount required"). Splitting the sheet's state into a reducer is a separate, purely local tidy-up.

Benefits

Locality: ACC-39 lives wholly on the server; one request, one transaction. Tests: wallet resolution becomes testable in pytest. Speculative because the sheet's instant feedback is a UX choice, and server round-trips for validation may feel worse on phone — worth a grilling, not a refactor yet.

What was built (2026-10-12)

All six candidates were accepted. Full backend suite and frontend tests pass. One test, test_phase14::test_passkeys_are_off_unless_the_server_turns_them_on, was already failing before this work.

  • #1 Bill placement: new pure module app/core/utils/billing.py with three functions:
    • bill_due: which bill a charge lands on.
    • on_a_bill: the projection's form of the same question.
    • due_now: what is due now.
    account_service._bills, the card's and the loan's due-now figure, the projection, and installment_conversion.default_start all ask it. _lands_on_bill, _bill_on_or_after and _due_on_or_after are gone. Tested directly in tests/test_billing.py.
    Bug fixed on the way: two loan plans due the same day are now both held in due-now. Before, only the first one was, while Months ahead treated both as held.
    Not done: the two FIFO payment loops stay separate. They record different things, and merging them would not pass the deletion test.
  • #2 What you owe: AccountView.owed_with_plans is set on every account in OWES. Overpaying never takes it below the plans still owed, which is the card's existing rule. The payoff planner, the assistant's cash skill, the account page and the tile all read this field. payoff._owed, the frontend's owedWithPlans and the unused shownFigure are deleted.
  • #3 Postings: list_accounts, get_account, statement and update_account now read the ledger's postings themselves. postings= only overrides them. Ten callers stopped passing them.
    Dead code removed: _unpaid_installments and unpaid_by_account.
  • #4 Account kinds: each side has one copy of the type rules, under the same names: account_service on the server, the top of lib/accounts.ts on the client.
    • tests/test_account_kinds_parity.py reads the TypeScript and fails if the two disagree.
    • New LOANS and isLoan.
    • The separate OWED_TYPES and SPREADS_ON are gone.
    Changed from the card: the rules are not sent per account over the API. Keeping one copy per side, with the parity test, gives the same single place to change with less code.
  • #5 Assistant skills: router.SKILL_TABLE lists every skill once, with its prompt line, or None if only the rules can choose it. SKILLS, MODEL_SKILLS, the ROUTE prompt (byte-identical to before) and the model check are all built from it. skills.handlers() must cover every name, and a test holds them together.
    Correction: the "13 vs 17" drift in the card above was intentional. The four missing skills are the ones the model must never choose.
  • #6 Wallet: POST /transactions now accepts -1 for a blank side. transaction_service._untracked_side creates the wallet and refuses unless the other side is a loan. Before, only the browser enforced that.
    • The sheet sends one request.
    • POST /accounts/untracked and untrackedCash() are deleted.
    • The sheet's instant checks (problem()) stay as they are. They switch the Save button on and off; the server's checks remain the ones that decide.

Top recommendation: #1 Bill placement

It's the highest-stakes rule in the hottest file: it decides money shown as due on Home, cash on hand, and Months ahead. It has been reimplemented three times, drifted once already (the 2026-09-16 fix noted in the docstring), and the last two feature commits both extended it. The extraction follows a pattern the repo already trusts — pure helpers in core/utils fed by a service (interest.py, payoff.py, affordability.py) — and existing tests (test_card_bills.py, test_card_app_bills.py, test_plan_payments.py) already pin the behaviour through public functions, so they survive the move unchanged.

#2 is the cheapest real win (a live disagreement fixed by deleting code) and could ride along or go first as a warm-up.
