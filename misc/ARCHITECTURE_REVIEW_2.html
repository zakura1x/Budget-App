A · Placing a message: one routing module the conversation can be tested through

Strong

Files assistant_service/turn.py _turn 155–195 · router.py small_talk, by_rules, follow_up (568, 574), by_model, merge, NOT_CARRIED · turn.context_intent

Problem

The order a message is placed in lives inside _turn, mixed in with memory, model metering and the facts call:

  1. small talk
  2. rules
  3. the Explain-link context
  4. follow-up
  5. the model
  6. loose follow-up

"Can the previous turn be carried?" is decided in four places: the NOT_CARRIED filter, the draft override in turn.py, and two special cases in follow_up. Every recent assistant commit (a73849c, 932e860, bd19830, 9228c66) tweaked this order. Each fix had to be tested through a whole turn.

Solution

One pure routing module: given the message, the earlier turns, the screen it came from, and a model-asking function, it returns the intent. _turn keeps memory, metering, facts and the reply. The carry rule moves into that module once, beside NOT_CARRIED.

Benefits

Locality: the next "follow-ups should…" fix is one file. Leverage: both the turn and scripts/ai_eval.py place questions the same way. Tests: conversation cases become plain calls with a fake model function, with no session, memory or meter. The 21 tests in test_ai_conversation get cheaper and sharper.

B · Money strings: isZero / negate belong in lib/money.ts

Strong

Files isZero in CreditDetails.tsx:19 (re-exported to Accounts.tsx), StatementSheet.tsx:46, Home.tsx:45, inline in AccountSheet.tsx:295 · negate in Home.tsx:46, Accounts.tsx:55, AccountDetail.tsx:48 (negateAmount), AccountSheet.tsx:106 · bare === '0.00' in CardBills, Calendar, AccountDetail, InstallmentFields, Emergency

Problem

Money is a string everywhere, on purpose (no floats). But the two most common questions about a money string are answered in nine places, and the four negate copies differ:

  • Home's has no zero guard, so "0.00" becomes "-0.00". Today's callers only pass negatives, so it doesn't show yet.
  • negateAmount's regex misses "-0.00".

A bare === '0.00' also misses "0" and "-0.00".

Solution

Export isZero and negate from lib/money.ts, which already has a private isZero inside splitDecimal. Use the guarded, normalising negate, then delete the copies and replace the bare comparisons.

Benefits

The deletion test passes outright: nine copies collapse into two exported helpers. Locality: the money-string rules sit with toDecimalString and centavos. Tests: one vitest file pins "0", "-0.00" and "0.00"; nothing tests these today. Small and mechanical.

C · Plan creation as recurring_service's own interface

Worth exploring

Files installment_conversion.py 84, 90, 131, 152–172 · recurring_service.py _pure 1640, _clean 1560, _expand 1356, create_rule 623, installment_plan 327, _apply_prepayment, _due_part, _installment_status, _reprice

Problem

REC-34 conversion reaches into three private functions under noqa: SLF001. After _clean, it patches the rule dict by hand: posted_through, pauses, skips, closed_on, from_transaction. So it knows recurring's internal layout. A field added to a rule must be remembered there too.

Separately, about ten concepts share one 1,841-line module. The installment arithmetic (_apply_prepayment, _due_part, _installment_status, _reprice) has no tests of its own; it is reached only through a database session.

Solution

Two steps, smallest first:

  1. Give recurring_service a public way to check a schedule without the database, and to create a plan from a payload plus what it was made from. Conversion uses only those, and the three noqas go.
  2. Optionally, move the pure installment arithmetic into core/utils, the way billing.py went, so prepayment and repricing can be tested directly.

Benefits

Locality: the rule's layout is known in one module. Leverage: the next feature that creates a plan (an assistant draft that sets up an installment, say) gets the same entry point. Tests: REC-32 prepayment ("lower" or "shorten") becomes a table of plain cases. That is the money path with the most special cases.

D · Links between transactions as one table: cashback, transfer legs, plan rows

Worth exploring

Files transaction_service.py:

  • cashback: delete 502–507, deleted list 548, restore 589–595, _restore_group 613, _restore_problem 680–699, save 951–956, upsert 1107–1156, _view 1191
  • pair back-patch: 419, 471, 771, 841

Also backup_service/references.py.

Problem

The cashback link alone is handled in 9 places. Transfer legs use "create both, then back-patch pair_id", written out 4 times. Plan rows (recurring_on) and interest rows (interest_on) get their own branches in _restore_problem.

CLAUDE.md already warns that a new kind of link "must join both _restore_group and _restore_problem". That is locality held together by a note, as _lands_on_bill's docstring was.

Solution

Describe each kind of link once: which field joins the rows, whether they delete and restore together, and what blocks a restore. Delete, restore, the restore check and the Recently-deleted list then read that description. Writing a linked pair (the pair back-patch) becomes one helper.

Benefits

Locality: a new link is one entry. Tests: TXN-25's restore rules can be checked per link kind. Today they are covered only through test_cashback and the phase-11 tests.

Risk: this is the delete/restore path for real money rows. Worth a careful look; it is not a quick refactor.

E · The transaction draft: one reducer, cashback as its own sub-form

Worth exploring

Files TransactionSheet.tsx: open effect 277–386 (eslint exhaustive-deps off at 385), cashback state 263–268, defaults 450–479, serialising 550–563, UI 961–1009, split lines 442/517

Problem

Opening the sheet resets about 30 setters by hand in two branches. The edit branch does not reset repeating.

Likely bug, not yet reproduced: open Add, tap Recurring, close without saving, then Edit an entry. The sheet would show the repeat choices instead of the entry.

Cashback alone is six states plus defaults, checks, serialising and UI spread through the file. Nothing tests the sheet.

Solution

Move the draft's state behind one reducer whose start state is built from the entry being edited or the add preset, so every open starts complete. Cashback becomes a sub-form with a small interface: it hands back the cashback block, or null, or "leave it", plus its error.

Benefits

Locality: "what a fresh sheet looks like" is one function. A missed reset can't happen, and this one gets fixed. Tests: the start function and the cashback serialiser are plain functions that vitest can pin with no DOM, matching how src/tests/ works today.

F · Alerts carry their facts, not just English

Speculative

Files budget_service/alerts.py 51, 177 · screens/Home.tsx alertText 62–83 · turn.py _ALERTS 82 · AskTile.tsx 20

Problem

Home strips /^A card payment is due / off the server's sentence, because the alert carries no due date. That ties the screen to the wording in alerts.py:177. Home rewrites 8 of the 10 alert kinds by hand, and two kind→place tables (turn._ALERTS, AskTile.CARD_ALERTS) have to agree.

Solution

Add the missing facts to the alert (due_in_days, the amount). Home formats from fields, never from English. Optionally, one shared list of alert kinds.

Benefits

Removes a brittle coupling for a few lines. Speculative only because there's one known breakage point and it works today. A server wording change would silently garble Home.

Checked and not proposed

  • Generating the frontend's types from the API schema. There are 75 hand-written TS interfaces against about 88 schema classes. A field-by-field comparison of 7 pairs found no drift, only some optional (?) fields the server always sends. Adding a codegen step to a repo whose server has no Node would cost more than it saves. Not now.
  • account_service.py is still 2,051 lines. Pass 1 took out bill placement, postings wiring and the owed figure. The rest (valuations, interest settings, balance checks) is cohesive by account, and nothing failed the deletion test.

What was built (2026-10-12)

All six were accepted and built. The full backend suite and the frontend tests pass. One test, test_phase14::test_passkeys_are_off_unless_the_server_turns_them_on, was already failing before this work.

  • A · Routing a message: router.route() holds the whole order, and router.carried_from() picks the turn a follow-up continues (the NOT_CARRIED filter plus the draft case). turn._turn only feeds them. Seven direct tests in test_ai_conversation.py use a fake model.
  • B · Money strings: isZero and negate are exported from lib/money.ts, and the 5 copies are deleted.
    Root fix: the server's Money type now sends any zero as "0.00", never "-0.00". That makes the roughly 60 bare === '0.00' checks across the screens correct without editing them. Tested in money.test.ts and test_money_schema.py.
  • C · Plan creation: recurring_service gained three public functions:
    • installment_schedule: checks a plan's terms, used by the preview.
    • add_plan: writes the plan with recurring's own bookkeeping fields and checks the rule limit. It does not commit, so a conversion stays a single commit.
    • post_due: posts the payments already due.
    The three noqa: SLF001 reach-ins are gone.
    Not done: moving the installment arithmetic. It was already pure behind installment_plan, so moving it would only have relocated code. It now has direct tests for "shorten" and "lower" instead.
  • D · Linked rows: two functions define which rows travel together: _goes_with (a transfer's legs, a purchase's cashback) and _listed_under. Delete, Recently deleted and Restore all read them. One helper, _write_pair, now writes a new transfer's two legs; the code that did this was repeated 3 times before.
  • E · Transaction draft: one Draft in lib/transactionDraft.ts, set whole by startDraft every time the sheet opens. cashbackPart builds what is sent.
    Bug fixed: choosing "Recurring" while adding left the next Edit open on the repeat choices.
    Not done: the full reducer rewrite. The form's fields are now one value, with one setter per field built from it; rewriting every interaction in an untested UI was the risky part.
  • F · Alerts: card_due and the two subscription alerts carry when ("today", "in 3 days"), and Home reads it instead of cutting up message. The two kind→place tables (turn._ALERTS, AskTile) were left as they are.

Top recommendation: A, routing a message

It's the hottest area left: four of the last nine commits tuned it, and every one of them had to be tested through a whole turn. Pulling the order and the carry rule into one pure module turns each future "the assistant misread my follow-up" report into a one-line test case. The model is already passed in as a function (ask_json), so a fake model makes it testable without the SDK.

B is the cheap, certain one: half an hour, and it removes a latent -0.00. E probably hides the repeating bug, so it's worth reproducing that first; if it's real, fix it now on its own, whatever happens to E.
